1. Turso Auto-Commit:
   - Every SQL execution is immediately committed
   - No need to call .commit() explicitly
   - Consider network latency when designing for high-throughput

2. Fallback Behavior:
   - If TURSO_DATABASE_URL is not set → uses local sqlite3
   - If libsql-client is not installed → falls back to sqlite3
   - Errors are logged (not silent)
   - Bots continue to run (graceful degradation)

3. Per-Database Configuration:
   - Each bot can have its own Turso URL/Token
   - Set TURSO_URL_<NAME> and TURSO_TOKEN_<NAME>
   - Falls back to main TURSO_DATABASE_URL and TURSO_AUTH_TOKEN

4. Git History Sanitization:
   - Old credentials may still exist in git history
   - Use BFG Repo-Cleaner to remove: bfg --delete-files token.txt
   - Force-push (if no other contributors): git push --force-with-lease

5. Health Check Frequency:
   - Should be called on startup and periodically
   - Detects database connectivity issues early
   - Add monitoring/alerting on failures

Issue: "libsql_client not installed"
  → pip install libsql-client
  → Or bot will fallback to local sqlite3

Issue: "Database connection refused"
  → Check TURSO_DATABASE_URL and TURSO_AUTH_TOKEN
  → Verify network connectivity to Turso
  → Check /api/health endpoint

Issue: "Unauthorized" on API endpoints
  → Verify Authorization header: Authorization: Bearer <ADMIN_TOKEN>
  → Check ADMIN_TOKEN is correctly set in wrangler secrets

Issue: "Worker deployment failed"
  → npx wrangler login
  → Verify wrangler.toml configuration
  → Check npm run deploy command

Issue: "Bots not starting in Termux"
  → Check ~/.env exists and is readable
  → Verify all required tokens are set
  → Check start_all.sh permissions: chmod +x start_all.sh
  → Tail logs: tail -f ~/.skteam_services/*.log
